# Approval tokens

Scoped approval tokens authorize specific destructive or side-effect
capabilities against specific targets within a specific engagement. This
document describes the token format, generation, verification, and
production deployment path.

## When tokens are required

A capability requires an approval token when its `SafetyProfile` has
`ApprovalPolicy.SCOPED_TOKEN`, or when a target-interacting capability
is mutating (`RiskLevel >= SIDE_EFFECT`). The execution policy rejects the
run without a valid token.

## Token format

Tokens are two-part strings separated by a dot:

```
<base64url-payload>.<base64url-signature>
```

The payload is a JSON object with these fields:

| Field | Type | Description |
|-------|------|-------------|
| `engagement_id` | string | Must match the engagement plan's ID |
| `capabilities` | list[string] | Capability IDs this token authorizes |
| `targets` | list[string] | Hostnames or IPs this token permits (normalized to lowercase, trailing dots stripped) |
| `parameters_sha256` | string | SHA-256 hex digest of the canonical JSON-serialized parameters (optional; required when the capability has phase-specific parameters) |
| `exp` | int | Unix timestamp after which the token is rejected |

### Parameter binding

When `parameters_sha256` is present, the verifier computes
`parameters_digest(parameters)` — a SHA-256 hash over
`json.dumps(parameters, sort_keys=True, separators=(",",":"))` — and
compares it to the token's digest. This binds the token to the exact
parameter set approved for the phase.

## Token generation

Tokens are generated by your internal authorization service. For
development and testing, generate one with the built-in HMAC signer:

```python
import base64, hashlib, hmac, json, time

key = "your-hmac-key"  # same as ADAF_APPROVAL_HMAC_KEY

payload = {
    "engagement_id": "ENG-2026-001",
    "capabilities": ["shadow-creds", "rbcd"],
    "targets": ["10.0.0.10", "dc01.corp.local"],
    "exp": int(time.time()) + 3600,  # 1 hour
}

encoded = base64.urlsafe_b64encode(
    json.dumps(payload).encode()
).decode().rstrip("=")

signature = base64.urlsafe_b64encode(
    hmac.new(key.encode(), encoded.encode(), hashlib.sha256).digest()
).decode().rstrip("=")

token = f"{encoded}.{signature}"
```

## Verification

`verify_scoped_approval()` in `core.engagement` performs these checks in
order:

1. Split the token at `.` and decode the base64url payload.
2. Recompute the HMAC-SHA256 signature; reject on mismatch (constant-time
   comparison via `hmac.compare_digest`).
3. Verify `engagement_id` matches the current plan.
4. Verify the requested `capability` is in the token's `capabilities` list.
5. Verify the `dc_ip` (normalized) is in the token's `targets` list.
6. Validate that all target-bearing phase options (see `_TARGET_OPTION_KEYS`)
   fall within the token's target scope.
7. If the request has parameters, compare `parameters_sha256` against the
   computed digest.
8. Check `exp` against the current UTC time; reject expired tokens.

## CLI usage

Pass the token and engagement ID on the command line:

```bash
adaf-attack run shadow-creds -d corp.local --dc-ip 10.0.0.10 \
  --force --approval-token "$TOKEN" --engagement-id ENG-2026-001
```

Or set it via environment variable:

```bash
export ADAF_APPROVAL_TOKEN="$TOKEN"
adaf-attack run shadow-creds -d corp.local --dc-ip 10.0.0.10 \
  --force --engagement-id ENG-2026-001
```

For engagement-plan runs, supply a per-phase token mapping:

```bash
adaf-attack engagement run engagement.yaml \
  --workspace ./workspaces -u operator \
  --approval-tokens tokens.json
```

## Production deployment

The built-in HMAC verifier uses a symmetric shared secret
(`ADAF_APPROVAL_HMAC_KEY`). This is acceptable for single-operator
development and testing but introduces a key-distribution risk in
multi-operator production environments.

### HMAC production gate

When `ADAF_ATTACK_ENV` is set to `prod` or `production`, the HMAC verifier
is blocked by default. You must either:

1. **Use the built-in RS256 JWKS verifier** — set `ADAF_APPROVAL_JWKS_URL` or
   `ADAF_APPROVAL_JWKS_FILE` to the authorization service JWKS. Tokens must be
   compact JWS (`header.payload.signature`) with `alg=RS256`.
2. **Acknowledge HMAC risk** — set `ADAF_APPROVAL_HMAC_ACKNOWLEDGE_PROD=1` to
   accept the shared-secret verifier explicitly.

### Recommended production architecture

```
Authorization Service ──► Signs JWT with private key
                          (RS256 / ES256)
        │
        ▼
Operator receives short-lived token
        │
        ▼
ADAF-ATTACK ──► Verifies JWT against JWKS endpoint
                (public keys only; no shared secret)
```

The authorization service should:

- Issue tokens scoped to a single engagement, target set, and capability set.
- Enforce a short expiry (minutes to hours, not days).
- Log every issuance for audit correlation.
- Bind parameters when the engagement phase has specific options.
